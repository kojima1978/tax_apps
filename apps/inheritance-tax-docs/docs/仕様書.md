# 必要書類管理 — 仕様書

## 1. 概要

### 1.1 目的

所得税・贈与税・相続税などの申告に必要な資料の準備・確認・管理をサポートするWebアプリケーション。税理士事務所のスタッフが、顧客ごとに必要書類の収集状況を一覧管理し、印刷・Excel出力・JSON保存/復元が可能。

### 1.2 ユーザー

税理士事務所のスタッフ（担当者）

### 1.3 動作環境

- モダンブラウザ（Chrome、Edge、Firefox、Safari）
- Docker環境（開発・本番）。画面は Vite でビルドした SPA、参考資料だけ Express 5 + SQLite のサーバーが持つ（§5.4）

## 2. 書類リスト種別

1ページ内でドロップダウン切替。種別ごとにlocalStorageで自動保存。

| 種別キー | ラベル | 説明 |
|----------|--------|------|
| `inheritance-tax` | 相続税申告 | 相続税申告に必要な全書類の管理（11カテゴリ） |
| `simplified` | 相続シミュレーション | シミュレーション用に必要最小限の書類（1カテゴリ） |
| `unlisted-stock` | 非上場株式評価 | 非上場株式評価に必要な書類の管理（5カテゴリ） |

種別切替時、現在のデータはlocalStorageに保存され、切替先のデータが復元される。

### 4.4 データモデル

#### ソースデータ（マスターデータ）

```typescript
interface DocumentItem {
  id: string;
  name: string;
  description: string;
  howToGet: string;
  canDelegate?: boolean;
}

interface CategoryData {
  id: string;
  name: string;
  documents: DocumentItem[];
}
```

#### ランタイムデータ（編集可能）

```typescript
interface SpecificName {
  id: string;
  text: string;
}

interface EditableDocument {
  id: string;
  name: string;
  description: string;
  howToGet: string;
  canDelegate: boolean;
  checked: boolean;
  checkedDate?: string;
  excluded: boolean;
  urgent: boolean;
  specificNames: SpecificName[];
  isCustom: boolean;
}

interface EditableCategory {
  id: string;
  name: string;
  documents: EditableDocument[];
  isExpanded: boolean;
  isDisabled: boolean;
}

type EditableDocumentList = EditableCategory[];
```

ソースデータ（`CategoryData[]`）は初期化時に `EditableDocumentList` に変換される。すべての状態はドキュメントオブジェクト内に統合（overlay-maps不使用）。

#### Excel出力

- xlsx-js-style によるスタイル付きExcelファイル生成

- 提出済み書類の非表示オプション
- ヘッダー: タイトル・依頼者名・被相続人名（相続税申告のみ）・担当者・発行日・事務所名
- フッター: 留意事項・事務所住所・連絡先

#### JSON保存/読込

- 設定をJSONファイルとして保存
- JSONファイルから設定を復元
- バージョン管理: v2.0.0（EditableDocumentList形式）

### 5.4 参考資料ページ（/resources）

専用ページで相続手続きに関する参考資料を提供。**データはサーバーの SQLite（`/app/data/resources.sqlite`）が持ち**、画面から追加・編集・削除・ドラッグでの並び替えができる。

#### 1件の中身

| 項目 | 説明 |
|------|------|
| タイトル | 必須 |
| 説明 | 任意 |
| ファイル / 外部リンク | どちらか。ファイルはアップロード（50MBまで、同名があれば `_<時刻>` を付ける）、外部リンクは新しいタブで開く |

#### API（`server/routes/resources.ts`）

| メソッド | パス | 内容 |
|------|------|------|
| GET | `/inheritance-tax-docs/api/resources/` | 一覧（`sort_order` 順） |
| POST | `/inheritance-tax-docs/api/resources/` | 追加（multipart、`file` は任意）。タイトルが無ければ 400 |
| PUT | `/inheritance-tax-docs/api/resources/:id` | 更新。ファイルを差し替えると古いファイルは消す。`removeFile=true` でファイルを外す |
| DELETE | `/inheritance-tax-docs/api/resources/:id` | 削除（ファイルも消す） |
| PATCH | `/inheritance-tax-docs/api/resources/reorder` | `{ ids: number[] }` の順に並べ直す |
| GET | `/inheritance-tax-docs/files/<ファイル名>` | アップロードしたファイル（`/app/data/uploads`） |
| GET | `/inheritance-tax-docs/api/health` | DB を開いて読めることと、DB ファイル・フォルダに書けることを見る。だめなら 503 `{status:'degraded',database:<コード>}` |

### 5.5 委任状（/power-of-attorney）

委任状と復代理委任状を刷る画面。**画面の入力は保存しない**（閉じると消える）。また使う人だけ DB に残す。

#### 画面の配置

- 幅 1024px 以上は**左に入力・右に印刷イメージ**を並べ、それぞれの中だけをスクロールする（ページごと流すと、下の入力欄を触っている間に右が関係ない紙へ流れる）。それより狭い画面は縦に積む
- 印刷イメージは既定で**枠の幅に合わせて縮める**（実寸より大きくはしない）。上の帯で「実寸」に切り替えられる。縮めるのは画面だけで、印刷では外す
- 上の帯に枚数と紙ごとのボタン（押すとその紙へ移動し、いま見ている紙を色付きで示す）。印刷できない間は理由（生年月日の誤り・委任事項が未選択）もここに出す
- 委任者の欄に入ると、横並びのときだけその人の紙を右に出す（縦積みでは画面が入力欄から離れてしまうので動かさない）

#### 生年月日の入力

- `［元号▼］［年］年［月］月［日］日` の4つの欄。元号のプルダウンは空（「元号」）から始まり、未入力のまま元号が出ることは無い。数字の欄は全角を半角に直し、数字以外は受け付けない（2桁まで）。元年は「1」と入れ、紙には「元年」と刷る
- 西暦では入れない。日付がそろうと横に「（1970年）」と西暦を添える
- 全部空欄なら手書き扱いで可。一部だけなら「年月日をそろえてください」、元号だけ無ければ「元号を選んでください」。存在しない日付・元号の範囲外は従来どおり弾く（誤りがある間は印刷も DB 登録もできない）
- 保存の形は従来どおり「昭和45年3月2日」の文字列（DB の変更なし）。既存の値は開くときに4つの欄へ分ける。委任状の画面（被相続人・委任者・復代理人）と DB の編集ダイアログで同じ部品を使う

#### 資料が必要な人（3ケース）

| ケース | 委任者 | 被相続人の欄 | 委任者の区分 |
|------|------|------|------|
| 亡くなった方（被相続人） | 相続人 | あり（氏名・生年月日を刷る） | 1人ずつ個人／法人を選ぶ（法人の受遺者があるため） |
| 存命の個人（本人） | 本人 | なし | 個人に固定。DBから選ぶときも個人だけ出す |
| 法人 | 法人 | なし | 法人に固定。DBから選ぶときも法人だけ出す |

#### 委任日

既定は空欄（手書き）。「日付を選ぶ」でカレンダーから選んだ日を和暦で刷る。委任状と復代理委任状で同じ日付を使う。

#### 被相続人DB・委任者DB（/power-of-attorney/principals）

- タブは「被相続人」（既定）と「人・法人（委任者）」（`?tab=people`）。委任状の画面のヘッダー「DB（被相続人・委任者）」と、各欄の見出しの「DBを開く」から新しいタブで開く
- 被相続人と委任者は**多対多**（二次相続では同じ相続人が2人の被相続人につながる）。つなぎ替えは被相続人タブの相続人チップ（×で外す・「相続人を足す」）か、委任状の画面から行う
- 委任状の画面で被相続人をDBから選ぶと、つながっている相続人もまとめて入れるかを聞く（空いている欄から埋め、もう入っている人は入れない）。被相続人をつないだまま委任者をDBに登録すると、その人も相続人としてつながる
- 「委任状を作る」は `?deceased=<id>`（相続人ごと）／`?principal=<id>` で委任状の画面を開く
- **相続税案件管理とは連動しない**。どちらもゴミ箱（論理削除）から戻せる。更新は `version` の楽観ロック（食い違えば 409 と今の内容）
- 被相続人DBを作る前に委任者ごとに書いていた被相続人の名前（`deceased_name`）は、起動時のマイグレーションで被相続人DBへ1回だけ移す。元の列は消さない

| メソッド | パス | 内容 |
|------|------|------|
| GET | `/inheritance-tax-docs/api/poa-deceased?q=&deleted=` | 一覧（相続人の名前でも引ける）。各行に `heirs` |
| POST / PUT / DELETE | `/inheritance-tax-docs/api/poa-deceased[/:id]` | 登録・更新（`version` 必須）・ゴミ箱へ |
| POST | `/inheritance-tax-docs/api/poa-deceased/:id/restore` | ゴミ箱から戻す |
| POST | `/inheritance-tax-docs/api/poa-deceased/:id/heirs` | `{ principalIds }` を相続人としてつなぐ（版は上げない） |
| DELETE | `/inheritance-tax-docs/api/poa-deceased/:id/heirs/:principalId` | つながりを外す（委任者は消えない） |
| GET / POST / PUT / DELETE | `/inheritance-tax-docs/api/poa-principals[/:id]` | 委任者DB。各行に `deceased`（つながっている被相続人） |

## 7. 非機能要件

### 7.1 パフォーマンス

- Viteによる高速ホットリロード（開発時）
- React.memo による不要な再レンダリング防止（SortableCategoryCard, SortableDocumentItem）
- useMemo / useCallback によるコールバック安定化
- manualChunks: react / dndkit バンドル分離
- useRef による最新値参照（DnDハンドラーの依存配列安定化）

### 7.2 データ保全

- localStorage自動保存（種別ごとに独立キー）
- JSON保存時のバージョニング（v2.0.0）
- 旧データ形式の後方互換（v1.0 overlay-maps → v2.0 EditableDocumentList 変換）
- useToast のタイマーリーク防止（アンマウント時クリーンアップ）

### 7.3 印刷対応

- `hidden print:block` によるレイアウト切替
- リスト型レイアウト（1列/2列対応）
- 印刷専用ヘッダー（事務所情報・担当者連絡先）
- 印刷専用フッター（留意事項・事務所住所）
- 操作ボタン等は印刷時に非表示（`no-print` クラス）
- 提出済み書類の印刷非表示トグル
- `break-inside-avoid` でカテゴリの途中改ページを防止

### 7.4 アクセシビリティ

- セマンティックHTML: `role`, `aria-expanded`, `aria-checked`, `aria-label`
- キーボード操作: Enter/Space で展開、Escape でキャンセル
- ドラッグ&ドロップ: キーボードセンサー対応（`sortableKeyboardCoordinates`）
- モーダル: フォーカストラップ、Escape で閉じる

## 10. デプロイ

```bash
# 起動（モードを変えるときもこれ。dev は --prod を外す）
docker/scripts/manage.sh start --prod inheritance-tax-docs

# 再ビルド（稼働中のモードを踏襲）
docker/scripts/manage.sh build inheritance-tax-docs
```

Nginx ゲートウェイ経由で http://localhost/inheritance-tax-docs/ にアクセスする（upstream は `inheritance-tax-docs:3003`）。素の `docker compose up` は本番を dev に作り替えるので使わない（個別に `-f docker-compose.prod.yml` を並べるのも不可）。

### 10.1 開発環境

- Dockerfile の `dev` ステージ（`USER node`）。`npm run dev`（`tsx watch server/index.ts`）で、Express に Vite をミドルウェアとして組み込み画面と API を 3003 で配信する（HMR の WebSocket も同じポート、`VITE_HMR_CLIENT_PORT` で変更可）
- 監視は `CHOKIDAR_USEPOLLING`（Dockerfile の ENV）でポーリング。Windows の bind mount では inotify が届かないため
- `./src` `./server` `./public` `./index.html` を読み取り専用で bind mount、データはボリューム `inheritance-tax-docs-data`（`/app/data`）
- メモリ 512M（予約 128M）、`NODE_OPTIONS=--max-old-space-size=384`

### 10.2 本番環境

- Dockerfile の `runner` ステージ（`USER node`）。Express が `dist/` の画面（SPA フォールバック付き）と API を 3003 で配信する
- bind mount なし（`volumes: !override` でデータのボリュームだけ）
- メモリ 192M（予約 64M）、`NODE_OPTIONS=--max-old-space-size=128`
