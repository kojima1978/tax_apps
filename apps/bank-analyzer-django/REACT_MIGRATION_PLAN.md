# bank-analyzer React 移行計画書

作成: 2026-10-07 ／ 対象: `apps/bank-analyzer-django` → 新アプリ `apps/bank-analyzer`

## 1. 目的と結論

- **目的**: 今後の機能追加を、ほかのアプリと同じ構成（Vite + React + Hono + Prisma + PostgreSQL）で
  行えるようにする。あわせてイメージを軽くする（471MB → 250MB 前後の見込み）
- **やり方**: 一度に入れ替えない。**いまの Django の挙動を「正解」として記録 → 新アプリを横に作る →
  同じ入力で突き合わせる → 切り替える**の順に進める
- **作業中のルール**: 移行が終わるまで **Django 側に機能を足さない**（不具合の修正だけは可。
  そのときは正解の記録も作り直す）。足したい機能は切り替えの後、新アプリに入れる

## 3. pandas が黙ってやっていること（要判断）

取込処理（`analyzer/lib/importer.py`）に、使い捨てコンテナで実際の入力を流して確かめた。
新アプリで**同じにするか、直すか**を決める必要がある。

| # | 入力 | いまの結果 | 問題 | 提案 |
|---|---|---|---|---|
| 1 | 口座番号 `0012345` | `12345` | **先頭の0が消える**（数値とみなされる） | 直す（文字列のまま読む） |
| 2 | 残高が空欄の行 | 残高 `0` | 残高チェックで誤って不整合になる | 直す（空欄は「残高なし」） |
| 3 | 和暦と西暦が混在（`R3.4.1` と `2021/4/2`） | **ファイルごと取込失敗** | 1行目の書式に他の行を合わせようとする | 直す（行ごとに判定） |
| 4 | 金額 `100.7` | `100` | 小数が黙って切り捨てられる | 直す（エラーにして行番号を出す） |
| 5 | `04/03/2021` | 2021年4月3日 | 米国式（月/日/年）で読む | エラーにする（日本の通帳では出ない書式） |

直す項目は、正解の記録（§5 段階1）で「Django と違って正しい」と明記したうえで違いを許す。
**2026-10-07 承認: 5項目とも提案どおり直す**。#3 は段階1でさらに広いと分かった
（西暦どうしの `2021-04-03` と `2021/4/4`、空行1つ、xlsx の日付セルと文字列の混在でもファイルごと失敗）。

### 段階1で見つかった追加の挙動（2026-10-07 承認: 提案どおり）

| # | 挙動 | 影響 | 提案 |
|---|---|---|---|
| 6 | CSV に口座番号列があると、**プレビューで重複が1件も出ない**（番号が数値のまま重複キーに入り、DB の文字列と一致しない）。取込時にサーバが判定し直して黙ってスキップする | 重なったファイルを入れても画面が警告しない | 直す |

| 8 | 分類は文字の正規化をしない（半角カナの摘要が全角のキーワードに当たらない）。NFKC は絞り込み検索にだけ効く | 分類の当たり方が文字種で変わる | **同じにする**（直すと実データの分類結果が変わるため、切替後に別途） |
| 9 | 同じ口座番号は銀行が違っても1口座にまとまる | 番号の重なる2行の口座が混ざる | 同じにする（表の作りがそうなっている。§6 で DB を変えない方針） |
| 10 | 全角数字の金額・`令和3年4月1日`・列名 `年月日`/`払戻`/`残高` は読めない。`-100` は出金 −100 | 取込できない書式がある | 同じにする（機能追加として切替後） |

## 5. 進め方

### 段階1: いまの挙動を「正解」として記録する

- Django に管理コマンド `dump_golden` を1本足し、次を JSON に書き出す:
  取込結果（`load_csv` + 残高チェック + 重複判定）、分類結果（分類・点数）、表記ゆれの候補、
  資金移動のペア、多額取引、月次の入出金表、各出力（CSV / Excel のセルの値 / JSON）
- 入力は2系統:
  - **リポジトリに入れてよいもの**: `data/dummy_csv` の3件 + §3 の境界ケースを集めた CSV / xlsx
    → `test-data/golden/` に置いて新アプリのテストが毎回読む
  - **実データ**: 稼働中の6案件。**リポジトリは公開なのでコミットしない**。リポジトリ外に書き出し、
    段階6の突き合わせにだけ使う
- 135件の pytest を、新アプリで書き直すテストの一覧として使う

### 段階2: 新アプリの土台を作る

- `apps/bank-analyzer` を作成。Dockerfile は非 root、compose は既存のアンカーをそのまま写す
  （`NODE_OPTIONS` を含む）。本番は `docker-compose.prod.yml` のオーバーレイで用意する
- 並行稼働の間は別のコンテナ名・ポートで動かす（例: `bank-analyzer-next` / 3008、パスは `/bank-analyzer-next/`）
- `bank-analyzer-test`（使い捨てのテスト用サービス）、`TEST_TARGETS`、CI を最初から入れる

### 段階3: 計算部分を移す（画面より先）

DB にも画面にも依存しない関数として書き、段階1の正解と突き合わせる。順番:

1. 和暦変換・文字の正規化・金額の読み取り
2. CSV / Excel の取込（§3 で決めた直し方を反映）
3. 残高チェック・重複判定（`wizard.py` の `make_dedup_key` 一式）
4. 分類（キーワード一致 → 表記ゆれ照合 → 贈与の閾値）
5. 資金移動の検出・多額取引
6. 月次の入出金表・各種集計

### 段階4: API を移す

URL 31本を Hono の API に置き換える。画面の HTML を返していたものは、データを返す API と画面に分かれる。
分類の変更履歴（取り消し）、範囲削除の控え（復元）は**DB の書き方まで同じ**にする（既存の履歴をそのまま使うため）。

### 段階5: 画面を作る

案件一覧 → 取込ウィザード → 直接入力 → 分析ダッシュボード（取引一覧・未分類・分類提案・資金移動・
データクレンジング・付箋・パターン管理の7タブ）→ 設定 → 通帳有無一覧 → お客様への依頼書（印刷）。
ファイル名は全アプリ共通の `R081005_名前_アプリ名.ext` に合わせる。

### 段階6: 並行稼働で突き合わせる

- 本番 DB の**複製**（`backup.sh drill` と同じ要領で使い捨て DB に復元）を新アプリにつなぐ。
  **同じ DB に2つのアプリが同時に書かない**
- 実データ6案件で、段階1の正解と新アプリの結果を全部比べる。§3 で直した項目以外の差はゼロにする
- 実際の操作（取込・分類・出力・印刷）を画面で一通り試す

### 段階7: 切り替える

切り替え直前に `backup.sh` で全体バックアップを取ってから行う。

- 新アプリを本来の名前（コンテナ `bank-analyzer`、ポート3007、`/bank-analyzer/`）で本番起動
- 直すもの: `manage.sh` の `APPS` / `POSTGRES_APPS` / `PROD_SECRETS`（`DJANGO_SECRET_KEY` を外す）、
  `backup.sh` の `PG_TARGETS`・`BIND_TARGETS`（`data/` は不要になる）・`SETTINGS_TARGETS`、
  `backup_bank_analyzer_json`（Django の管理コマンドを呼んでいる）、ゲートウェイ、ポータルのリンク、
  `CLAUDE.md`、メモ
- **JSON バックアップの形式は今と同じに保つ**。過去の夜間バックアップの JSON から新アプリで復元できること

### 段階8: Django を片付ける

2〜4週間問題が出なければ `apps/bank-analyzer-django` を削除し、DB から Django 自身の表
（`auth_*` / `django_*`）を消す。

## 6. DB の扱い

- **データは移し替えない**。Prisma のモデルを既存の表名・列名に対応させる（`@@map` / `@map`）。
  今のボリューム `bank-analyzer-postgres` をそのまま使うので、移行に失敗してもデータは無傷
- `pg_trgm` の GIN インデックスは Prisma の定義では書けないので、マイグレーションの SQL に直接書く
- 最初のマイグレーションは「既存の表をそのまま受け入れる」形にする（`prisma migrate resolve` で適用済み扱い）
- 全体の設定（多額取引の閾値・分類パターンなど）は、ファイルではなく DB の表に置く
  （今は `data/user_settings.json` が無く既定値で動いているので、移す値は無い）

| リスク | 対策 |
|---|---|

## 段階3の結果（2026-10-08）

計算部分を `apps/bank-analyzer/server/lib/` へ移した（DB にも画面にも依存しない関数）。
型検査込み 422件成功。架空データの正解に加え、**集計は実データの正解（6案件）でも一致**を確認
（`BANK_ANALYZER_GOLDEN_DIR` を渡して手で回す。CI には載らない）。

| 段階3の項目 | ファイル | 突き合わせ |
|---|---|---|
| 1. 和暦・正規化・金額 | `dates.ts` / `text.ts` / `import/loadStatement.ts` | 単体 |
| 2. 取込 | `import/` | 各ファイルの読み取り結果 |
| 3. 残高・重複 | `balance.ts` / `dedup.ts` / `wizard.ts` | シナリオを丸ごと流してプレビューと取込件数 |
| 4. 分類 | `classify.ts` / `fuzz.ts` / `categories.ts` | rapidfuzz の点数・分類結果 |
| 5. 資金移動・多額 | `analyze.ts` | シナリオの最後に残った取引 |
| 6. 月次表・集計 | `aggregate.ts` | 月次表・ルール適用のプレビュー・分析画面（絞り込み9通り）・未分類のまとめ |

Django 版と同じにしたもの（直すなら別に決める）:

- 資金移動の印は付けるだけで外さない。取込のたびにファイル単位で案件の全取引を判定し直す
- 分析画面の資金移動の一覧は、保存した印ではなく表示のたびに判定し直す
- `sort=-amount_out` のような画面の並び替えの指定は読めずに日付順になる
  （記録の `sort_amount_desc` も実際は日付順）
- 未分類のまとめには要確認の印の付いた取引も入る（分類の候補・ルール適用のプレビューには入らない）

Django 版と違うもの（意図的）:

- 同じ日の取引の並びは (日付, id)。Django 版は pandas の安定でない並べ替えで、同じ日の順に
  規則が無かった（実データの1案件で資金移動の一覧の2行が入れ替わる。判定結果は同じ）
- 未分類が0件でも `aiGroups` は空の配列で返す（Django 版はキーごと無かった）
- 取込のとき摘要の空欄・残高の空欄は null のまま入れる（Django 版の画面は `''` / `0` にしていた）
- edge_files の取引 id 24 は資金移動にならない（相手だった小数の行を #4 で取り込まないため）

**資金移動の一覧の「相手」（2026-10-08 決定: 直す）**。Django 版は出金ごとの相手の入金を
「印の付いた入金のうち、相手の口座で金額が許容誤差以内の**最初のもの**」で選んでおり、日付を見ていない。
同じ口座へ同じ額を何度も移している案件では、2回目以降の出金にもすべて1回目の入金が並ぶ。
実データの正解では一覧の **74組中60組が、出金から3日より離れた入金を相手として表示**していた
（印そのものは正しく付いている。表示の組み合わせだけが違う）。
→ `detectTransfers` が判定で実際に組んだ相手（`partnerId`）を返し、一覧はそれを並べる。
正解との突き合わせは出金側だけにし、相手は「別の口座・許容誤差以内・期間内・同じ入金を
2つの出金が指さない」を実データ6案件で確かめている。相手が見つからない行（`destination: null`）は
もう出ない。
